# Loopwise

AI-powered clinic system for Philippine outpatient clinics: front desk, nurse, doctor, lab, pharmacy, cashier and the
patient, with Wise (the AI assistant) drafting the work at every desk and a person confirming it. Each deployment is a
single self-hosted instance for one business (one `organizations` row) with many clinic locations; there is no SaaS,
sign-up or tenant billing. Built on NestJS 11 + GraphQL code-first + Prisma/PostgreSQL + React. Read
[docs/PLAN.md](docs/PLAN.md) first for the product, modules and phases, then [docs/DESIGN.md](docs/DESIGN.md) for the
data model (§5), the follow-up state machine (§6), Wise (§7) and the access rules (§8). [docs/NEXT.md](docs/NEXT.md) is
the handoff: what is built and what comes next.

## Stack rules

- NestJS 11 on Express, GraphQL code-first (`@nestjs/graphql` + Apollo), one server, no federation. REST only for auth,
  agent streaming and file uploads.
- Prisma on PostgreSQL only. The schema is split by domain into
  `apps/api/prisma/schema/*.prisma` (generator and datasource in `main.prisma`; Loopwise-only models in `loopwise.prisma`,
  `chats.prisma`, `auth.prisma`, `usage.prisma`). Plural snake_case tables, UPPERCASE enum values, UUIDv7 ids,
  `timestamptz(3)`. Migrations: `0000_init` (generated by Prisma) and `0001_rls_and_triggers` (hand-written: RLS,
  triggers, checks, analytics); add new ones after them with `prisma migrate dev`.
- Frontend: React (TanStack Router, shadcn/ui on Radix + Tailwind v4, CSS Modules on the same tokens) following
  [docs/frontend-design.md](docs/frontend-design.md) and the shadcn UI kit look in [docs/design-system.md](docs/design-system.md),
  with Apollo Client + GraphQL Code Generator. Calls go through the `lib/*-api.ts` modules (`lib/apollo-procedures.ts`),
  typed by `lib/api-types.ts`; types of `apps/api` are imported with `import type` from `@loopwise/api/*`.
- Node from `.nvmrc` (`nvm use`), npm pinned by `packageManager` (`engine-strict`).

## Module conventions

- **kebab-case file names**: `invoice-totals.service.ts`, `patient-access.guard.ts`.
- One NestJS module per schema domain under `apps/api/src/clinical/<domain>/` (DESIGN.md §4.5): built `clinics`
  (document numbering), `reference`, `practitioners`, `patients`, `encounters`, `diagnostics`, `prescriptions`,
  `documents`, `billing`, `audit`, `wise-proposals`, `scribe`, `insights`, `reports`, `analytics` (plus `rls`); planned
  `scheduling`, `immunizations`, `philhealth`, `hmo`, `inventory`, `portal`. Large domains have sub-feature folders
  (`billing/invoices`, `diagnostics/worklist` …). Each has `<feature>.module.ts`, `.resolver.ts`, `.service.ts`,
  `.repository.ts`, `.loader.ts`, `dto/`, `models/`, and its enums registered in one place.
- Modules use each other only through exported services (or a reader token for Wise); no circular imports.
- **Resolvers (and REST controllers) stay thin**: parse args, check access via decorators, call a service, return. No
  business logic, no Prisma.
- **Business logic lives in services.** Each status flow goes through one transition function with guards. Errors are
  `DomainError` subclasses with a stable `errorCode` (`apps/api/src/common/errors/`). Log with Nest `Logger`.
- **Prisma is only used in repositories.** Services call repositories, never `PrismaService` directly. Raw SQL goes to
  Prisma TypedSQL (`prisma/sql/*.sql`) or `$queryRaw` inside a repository.
- Access control through decorators on a global `AuthGuard`: `@Public()`, `@CurrentUser()`, `@ClinicAccess()` (with
  `staffRoles` for a desk), `@OrgMember()`, `@OrgAdmin()`, `@ClinicAdmin()`. Staff hold roles per clinic
  (`user_clinic_roles`, mapped to access levels by `@loopwise/shared/staff-roles`).
- N+1: request-scoped DataLoaders, one `<feature>.loader.ts` per module.
- Background work (reminders): pg-boss jobs registered with `@Job(name)`.
- **Traceable:** every request has a correlation id (`x-request-id`), in the logs and in `audit_logs.request_id`.

## Clinical rules

- **Deny by default.** A user reaches a patient only through a `CareRelationship` (or a time-limited, logged
  break-glass), or a desk or lab role at the clinic of the visit (DESIGN.md §8). Clinical repositories run their queries inside the row-level security context (see
  `apps/api/src/clinical/rls/`), never on the bare `PrismaService`.
- **Encounter-centric.** Every clinical record hangs off an encounter (`encounter_id` required); children never store
  the patient or clinic again.
- **Audit everything.** Every view and change writes an `audit_logs` row through `AuditService`, in the same
  transaction. The table is append-only (a trigger rejects UPDATE and DELETE).
- **AI drafts, the clinician confirms.** Agent tools only read (scoped to the user) or render proposal cards. Only the
  confirm button calls the mutation that orders, refers, issues or messages. Critical values never get an automated
  patient message.
- **Synthetic data only.** Seeds, fixtures and demos never contain real patient data.

## Verify

Before calling any change done, run and pass:

```bash
npm run lint
npm test
```

Plus `npm run format:check`. For frontend changes also run `npm run test:e2e -w @loopwise/frontend` with the local stack
up (the chat flow makes one real LLM call).

## Local setup

```bash
nvm use
npm install
cp .env.example .env            # fill in BETTER_AUTH_SECRET and an LLM key
docker compose up -d --wait     # Postgres on localhost:5435, database `loopwise`
npm run db:deploy -w @loopwise/api   # apply Prisma migrations
npm run db:seed -w @loopwise/api     # synthetic demo data; test@test.test / test1234 (admin + doctor)
npm run dev:api                    # apps/api on :5006
npm run dev:frontend               # frontend on :3000, proxies the API to :5006
```
