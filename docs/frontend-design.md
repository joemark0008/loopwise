# Frontend design pattern

A reusable frontend pattern for a signed-in web application: folder structure, routes, app shell, navigation, and design system. It is independent of any product and backend.

**Everything named here is a sample.** `customers`, `reports`, the menu sections, the permissions, and the colours only show the pattern. Replace them with your system's own.

> **Loopwise's own values** (tokens, clinical status colours, fonts, components, table density, roles, the patient
> context and the Wise dock) are in [design-system.md](design-system.md). Where the two differ, design-system.md wins.

| Keep (the pattern)                     | Replace (the sample)                           |
| -------------------------------------- | ---------------------------------------------- |
| Folder structure and file naming       | Domain names such as `customers` and `reports` |
| Route zones, guards, and layout routes | Paths, feature keys, and permissions           |
| App shell structure and behaviour      | Logo, menu sections, and menu items            |
| Token names and how tokens connect     | Colour values and fonts                        |
| Sizing, responsive, and motion rules   | API endpoints and data client                  |

---

## 1. Stack

| Concern     | Sample choice                                                            | Can it change?                        |
| ----------- | ------------------------------------------------------------------------ | ------------------------------------- |
| Build       | Vite                                                                     | Yes                                   |
| UI          | React + TypeScript                                                       | The code samples assume it            |
| Routing     | TanStack Router, file-based                                              | The code samples assume it            |
| Components  | shadcn/ui (Radix primitives, `cva`, `cmdk`, `motion`) in `components/ui` | The theme and shell samples assume it |
| Icons       | `@tabler/icons-react`                                                    | Yes                                   |
| Styling     | Tailwind v4 (`@tailwindcss/vite`) + CSS Modules + CSS variables          | Keep the CSS variables                |
| Data client | Any: REST, GraphQL, or a query library                                   | Yes                                   |
| Auth        | Any, exposed through `fetchSession()`                                    | Yes                                   |

The pattern touches the backend in only two places: `fetchAppConfig()` and `fetchSession()`.

## 2. Principles

1. **The URL is the state.** Tabs, detail views, and wizard steps are routes or search params, so refresh, bookmarks, and the back button all work.
2. **Guards run before render.** A signed-out visitor never sees a flash of the app shell.
3. **Route files are thin.** They hold the path, guard, and search validation. Pages live in `feature/`.
4. **One nav config drives everything.** The sidebar, breadcrumb, search, shortcuts, and permission screen read the same array.
5. **Frontend gating is cosmetic.** Hiding a link improves the experience, and the server still enforces access.
6. **Components read tokens, never hex.** Themes and branding work by changing CSS variables.
7. **Sizes are in `rem`.** Changing the root font size scales the whole interface.
8. **Page layouts respond to the content area.** Container queries follow text size and sidebar width.

## 3. Folder structure

```
src/
├── main.tsx             Entry: router, providers, global CSS
├── routeTree.gen.ts     GENERATED by the router plugin
├── routes/              One thin file per URL
├── layout/              The signed-in shell
│   ├── AppLayout.tsx    Sidebar + top bar + page outlet
│   ├── PermissionGate.tsx
│   ├── Sidebar/
│   └── TopBar/
├── feature/             One folder per product domain
│   └── customers/
│       ├── index.tsx        List page
│       ├── detail/index.tsx Detail page
│       ├── components/      Tables, filters, modals
│       ├── hooks/           useCustomers, useCustomer…
│       ├── api.ts           Requests for this domain
│       ├── constants.ts     Labels, page size
│       └── css/             CSS Modules
├── components/          Shared across features (PageHeader, ErrorState…)
├── context/             Router context type
├── lib/                 Non-visual: config, session, navigation, appearance
└── theme/
    ├── index.css        Tailwind, the shadcn variants, and the token → colour mapping
    ├── tokens.css       All design tokens
    └── ui.module.css    Shared UI classes
```

Dependencies point one way: `routes` → `layout` and `feature` → `components` → `lib` and `theme`. Features don't import from other features, apart from a small shared domain such as permissions.

Feature hooks hide the data client and return plain values:

```ts
const { customers, totalCount, loading, error, retry } = useCustomers(filter);
```

## 4. Startup

```
1. Apply cached appearance from localStorage (avoids a text-size flash)
2. Render providers
3. __root.beforeLoad      → load app config
4. _protected.beforeLoad  → load session, or redirect to /login
5. AppLayout mounts       → load saved appearance, replace the cached copy
```

```tsx
// src/main.tsx
export const router = createRouter({
	routeTree,
	context: { config: undefined!, session: null } satisfies RouterContext,
	defaultPreload: 'intent',
});

declare module '@tanstack/react-router' {
	interface Register {
		router: typeof router;
	}
}

createRoot(document.getElementById('root')!).render(
	<StrictMode>
		<ThemeProvider>
			<TooltipProvider>
				<RouterProvider router={router} />
			</TooltipProvider>
		</ThemeProvider>
	</StrictMode>,
);
```

Keep the providers **above** the router. The root route's pending and error components replace its normal component, so a provider inside that route would be missing when they render. Radix needs no theme provider: the theme is CSS variables and the `dark` class on `<html>`.

Import global CSS in this order: `theme/reset.css` (its layer comes first), `theme/index.css` (Tailwind, `tw-animate-css`, the shadcn variants), then `theme/tokens.css` and the other theme files. Utilities live in Tailwind's layers and CSS Modules are unlayered, so a module class passed as `className` wins over a component's utilities.

## 5. Routes

### Route zones

| Zone      | File             | Guard                               | Sample use                                |
| --------- | ---------------- | ----------------------------------- | ----------------------------------------- |
| Root      | `__root.tsx`     | Loads app config                    | Everything                                |
| Protected | `_protected.tsx` | Needs a session; renders the shell  | The application                           |
| Public    | `_public.tsx`    | Signed-in users are redirected away | Login, forgot password                    |
| Top-level | None             | Own logic, or none                  | Links that must work in any session state |

Use the top-level zone for links sent to other people, such as a shared document, an invitation, or a password reset. These must not redirect a stranger to login, and they must not redirect a signed-in user into the app.

```
src/routes/

├── index.tsx                  "/" redirects to the start page or login
├── reset-password.tsx         Top-level
```

### File naming

| File                     | URL      | Meaning                                             |
| ------------------------ | -------- | --------------------------------------------------- |
| `_name.tsx`              | None     | Pathless layout: adds a guard or UI, no URL segment |
| `_name/child.tsx`        | `/child` | Child of that layout                                |
| `a.b.tsx`                | `/a/b`   | A dot is a path separator                           |
| `a.index.tsx`            | `/a`     | Index child of the `a.tsx` layout                   |
| `a.$id.tsx`              | `/a/:id` | Dynamic segment                                     |
| `a.tsx` beside `a.*.tsx` | `/a`     | **Layout parent; must render `<Outlet />`**         |

**Common trap:** `customers.tsx` beside `customers.$id.tsx` is that route's parent. If it renders the list and no `<Outlet />`, clicking a customer changes the URL while the page stays the same. Put the list in `customers.index.tsx`.

### Router context

```ts
// src/context/index.ts
export interface RouterContext {
	config: AppConfig; // Set by __root; present everywhere
	session: SessionUser | null; // Set by _protected
}

export interface AppConfig {
	name: string;
	features: Record<string, boolean>;
}
```

Guards run on every navigation, so cache one promise instead of refetching. Never cache a failure.

```ts
// src/lib/session.ts
let inFlight: Promise<SessionUser | null> | null = null;

export function fetchSession() {
	inFlight ??= loadSession().catch((err) => {
		inFlight = null;
		throw err;
	});
	return inFlight;
}

// Call after every sign-in and sign-out, before navigating.
export function invalidateSession() {
	inFlight = null;
}
```

`loadSession()` returns `null` when signed out and throws only on a real failure, so a guard can tell the two apart. `fetchAppConfig()` uses the same pattern.

Gating has three layers:

| Layer              | Where                         | Result when not allowed              |
| ------------------ | ----------------------------- | ------------------------------------ |
| Feature enabled    | Layout route `beforeLoad`     | Redirect                             |
| Role or permission | `PermissionGate` in the shell | "You don't have access to this page" |
| Enforcement        | Server                        | Refuses the data                     |

### Tabs are routes

The layout route owns the tab strip and anything else the tabs share.

```tsx
// routes/_protected/reports.tsx
const TABS = [
	{ value: 'overview', label: 'Overview', to: '/reports' },
	{ value: 'usage', label: 'Usage', to: '/reports/usage' },
] as const;

function ReportsLayout() {
	const navigate = useNavigate();
	const pathname = useRouterState({ select: (s) => s.location.pathname });
	const active = TABS.find((t) => t.to !== '/reports' && pathname.startsWith(t.to))?.value ?? 'overview';

	return (
		<Tabs
			value={active}
			keepMounted={false}
			onChange={(value) => {
				const tab = TABS.find((t) => t.value === value);
				if (tab) void navigate({ to: tab.to });
			}}
		>
			<Tabs.List mb='lg'>
				{TABS.map((t) => (
					<Tabs.Tab key={t.value} value={t.value}>
						{t.label}
					</Tabs.Tab>
				))}
			</Tabs.List>
			<Outlet />
		</Tabs>
	);
}
```

### Search params

- Treat the URL as untrusted: `validateSearch` checks each field, clamps values, and sets defaults.
- Keep fields optional, so plain links stay valid.
- Never put personal details in search params. They end up in browser history, shared links, and server logs.
- Check any redirect target taken from data, such as `?next=`:

```ts
export function sameSitePath(p: unknown): string | null {
	return typeof p === 'string' &&
		p.startsWith('/') &&
		!p.startsWith('//') &&
		!p.includes('\\') &&
		!/[\u0000-\u001f\s]/.test(p)
		? p
		: null;
}
```

```tsx
// src/layout/AppLayout.tsx
export function AppLayout() {
	const [mobileOpen, { toggle, close }] = useDisclosure(false);
	// Load and save this with the user's profile.
	const [chosen, setChosen] = useState<boolean | null>(null);

	const isDesktop = useMediaQuery('(min-width: 48em)') === true;
	const isWide = useMediaQuery('(min-width: 80em)') !== false;
	const collapsed = isDesktop && (chosen ?? !isWide);
	const toggleRail = () => setChosen(!collapsed);

	useHotkeys([['[', () => isDesktop && toggleRail()]]);

	return (
		<AppShell
			layout='alt'
			header={{ height: '3.75rem' }}
			navbar={{
				width: collapsed ? 72 : 240,
				breakpoint: 'sm',
				collapsed: { mobile: !mobileOpen },
			}}
			transitionDuration={200}
			transitionTimingFunction='cubic-bezier(.2,.8,.2,1)'
			padding='lg'
		>
			<AppShell.Header withBorder={false}>
				<TopBar mobileOpen={mobileOpen} onToggleMobile={toggle} />
			</AppShell.Header>
			<AppShell.Navbar withBorder={false}>
				<Sidebar collapsed={collapsed} onToggle={toggleRail} onNavClick={close} />
			</AppShell.Navbar>
			<AppShell.Main>
				<div className='app-page'>
					<PermissionGate>
						<Outlet />
					</PermissionGate>
				</div>
			</AppShell.Main>
		</AppShell>

```

- `layout="alt"` makes the sidebar full height, with the top bar beside it.
- The `sm` breakpoint must match in `AppShell`, the top bar's `Burger`, and the sidebar toggle, or the mobile drawer can get stranded.
- Always pass `onNavClick={close}`, or the drawer stays open over the new page.

### Sidebar

| Window width  | Default          | Behaviour                                              |
| ------------- | ---------------- | ------------------------------------------------------ |
| Below `48em`  | Drawer           | Overlay opened by the burger; always the labelled list |
| `48em`–`80em` | Rail, 72 px      | Icons with tooltips; groups open as flyout menus       |
| `80em` and up | Expanded, 240 px | Section labels; accordion groups                       |

The user's choice overrides the default on desktop.

From top to bottom, the sidebar contains:

1. **Brand row:** `3.75rem` tall to line up with the top bar. The logo links to the start page.
2. **Scope switcher** (optional): a workspace or team selector that narrows the menu.
3. **Pinned section** (optional): copies of the user's favourite pages. When a pinned page is current, only the pinned copy highlights.
4. **Labelled sections:** plain rows and accordion groups. One group is open at a time, and the group holding the current page opens automatically.

| Element                | Size and style                                                            |
| ---------------------- | ------------------------------------------------------------------------- |
| Section label          | `0.625rem`, weight 700, uppercase, `0.16em` tracking, muted               |
| Row                    | Minimum height `2.125rem`, `0.8125rem` text, weight 500, radius 8 px      |
| Active row             | Lighter background, strong text, weight 600, accent icon                  |
| Child row              | Minimum height `1.75rem`, a small dot instead of an icon, left guide line |
| Count badge            | `0.625rem` pill with accent fill                                          |
| Rail item with a count | Small dot instead of a number                                             |

Build the sidebar from shadcn's `Sidebar` parts (`SidebarHeader`, `SidebarGroup`, `SidebarMenuButton` …) in the `inset` variant with `collapsible='icon'`. The `--sidebar-*` variables point at the `--app-nav-*` tokens, so the rail, the active pill and the borders follow the theme without per-component styling. On a phone the same tree renders in a `Sheet`.

```tsx
<SidebarWrapper>
	<Sidebar variant='inset' collapsible='icon'>
		<SidebarHeader>{/* logo */}</SidebarHeader>
		<SidebarContent>
			<SidebarGroup>
				<SidebarGroupLabel>Desk</SidebarGroupLabel>
				<SidebarMenu>{/* SidebarMenuItem > SidebarMenuButton asChild tooltip={label} > Link */}</SidebarMenu>
			</SidebarGroup>
		</SidebarContent>
		<SidebarFooter>{/* user row */}</SidebarFooter>
		<SidebarRail />
	</Sidebar>
	<SidebarInset>{/* header + page */}</SidebarInset>
</SidebarWrapper>
```

### Top bar

From left to right:

1. **Burger:** mobile only.
2. **Breadcrumb:** derived from the nav config. `0.75rem`, weight 600, uppercase, `0.14em` tracking.
3. **Search field:** looks like an input and opens a command palette listing the pages the user can open.
4. **Notifications.**
5. **Account menu:** theme, text size, account links, sign out.

```ts
// The longest matching `to` owns the current path.
function owningLink(links: NavLink[], pathname: string) {
	return links
		.filter((l) => pathname === l.to || pathname.startsWith(`${l.to}/`))
		.sort((a, b) => b.to.length - a.to.length)[0];
}

function crumbs(links: NavLink[], pathname: string): string[] {
	const link = owningLink(links, pathname);
	if (!link) return [];
	const parts = [
		NAV_SECTIONS.find((s) => s.id === link.section)?.label,
		link.group && NAV_GROUPS[link.group].label,
		link.label,
	];
	if (pathname !== link.to) {
		const segment = pathname.slice(link.to.length + 1).split('/')[0];
		parts.push(link.tabs?.[segment] ?? 'Details');
	}
	// Drop consecutive duplicates, so ADMIN / ADMIN / USERS reads ADMIN / USERS.
	return (parts.filter(Boolean) as string[]).filter(
		(p, i, all) => i === 0 || p.toLowerCase() !== all[i - 1].toLowerCase(),
	);
}
```

### Keyboard shortcuts

| Keys                                 | Action                            |
| ------------------------------------ | --------------------------------- |
| `[`                                  | Collapse or expand the sidebar    |
| `/` or `⌘K`                          | Open search                       |
| `G`, then a letter within one second | Go to a page (`NavLink.shortcut`) |

`useHotkeys` ignores keys typed into inputs by default. For `⌘K` to work inside inputs too, register it separately and pass `[]` as the second argument.

### Sign-out order

1. Call the sign-out endpoint and check for an error.
2. Call `invalidateSession()`.
3. Clear the data client's cache without refetching.
4. Clear cached appearance settings, so the next person doesn't inherit them.
5. Navigate to `/login` with `replace: true`.
6. Call `router.invalidate()`.

## 7. Navigation config

`src/lib/navigation.ts` is the single source for the menu. `to` is typed from the generated route tree, so a link to a missing route is a compile error.

```ts
type AppPath = Extract<FileRouteTypes['to'], `/${string}`>;

export type NavSection = 'workspace' | 'records' | 'admin';
export type NavGroupId = 'reports' | 'setup';

export interface NavLink {
	icon: ComponentType<{ size?: number | string; stroke?: number }>;
	label: string;
	to: AppPath;
	section: NavSection;
	group?: NavGroupId; // Nest under an accordion or flyout
	exact?: boolean; // Match exactly, not as a prefix
	shortcut?: string; // 'G C'
	notifications?: number; // Badge count, filled in at runtime
	sidebar?: false; // Routable and searchable, but no sidebar row
	tabs?: Record<string, string>; // Path segment → breadcrumb label
	feature?: string; // Hide unless this feature is on
	can?: string[]; // Hide unless the user has one of these
}

export const NAV_SECTIONS: { id: NavSection; label: string }[] = [
	{ id: 'workspace', label: 'Workspace' },
	{ id: 'records', label: 'Records' },
	{ id: 'admin', label: 'Admin' },
];

export const NAV_GROUPS: Record<NavGroupId, { label: string; icon: NavLink['icon'] }> = {
	reports: { label: 'Reports', icon: IconReportAnalytics },
	setup: { label: 'Setup', icon: IconSettings },
};

export const navLinks: NavLink[] = [
	{ icon: IconHome, label: 'Home', to: '/home', shortcut: 'G H', section: 'workspace' },
	{
		icon: IconUsers,
		label: 'Customers',
		to: '/customers',
		shortcut: 'G C',
		feature: 'customers',
		can: ['customers.view'],
		section: 'records',
	},
	{
		icon: IconChartBar,
		label: 'Reports',
		to: '/reports',

		section: 'records',
		group: 'reports',
	},
	{

		label: 'Users',

		can: ['users.manage'],

```

The menu is built in two steps:

```ts
export function visibleNavLinks(links: NavLink[], config: AppConfig, permissions: string[]) {
	return links.filter((l) => {
		if (l.feature && !config.features[l.feature]) return false;
		if (l.can && !l.can.some((p) => permissions.includes(p))) return false;
		return true;
	});
}

export type NavEntry = { kind: 'link'; link: NavLink } | { kind: 'group'; id: NavGroupId; links: NavLink[] };

export function buildMenu(links: NavLink[]) {
	return NAV_SECTIONS.map((section) => {
		const entries: NavEntry[] = [];
		for (const link of links.filter((l) => l.section === section.id && l.sidebar !== false)) {
			if (!link.group) {
				entries.push({ kind: 'link', link });
				continue;
			}
			const group = entries.find(
				(e): e is Extract<NavEntry, { kind: 'group' }> => e.kind === 'group' && e.id === link.group,
			);
			if (group) group.links.push(link);
			else entries.push({ kind: 'group', id: link.group, links: [link] });
		}
		return { ...section, entries };
	}).filter((s) => s.entries.length > 0);
}
```

Empty sections and groups disappear on their own. The same config also drives the permission screen:

```tsx
// src/layout/PermissionGate.tsx
export function PermissionGate({ children }: { children: ReactNode }) {
	const pathname = useRouterState({ select: (s) => s.location.pathname });
	const permissions = usePermissions(); // null while loading
	const row = navLinks
		.filter((l) => l.can && (pathname === l.to || (!l.exact && pathname.startsWith(`${l.to}/`))))
		.sort((a, b) => b.to.length - a.to.length)[0];

	if (!row?.can || !permissions || row.can.some((p) => permissions.includes(p))) return <>{children}</>;
	return <Alert title={row.label}>You don't have access to this page. Ask an administrator if you need it.</Alert>;
}
```

## 8. Design system

### Shared UI components

Keep these in `components/ui`, not inside a feature. Radix handles behaviour such as menus, dialogs and focus; the classes handle appearance on dense screens.

| Component                                           | What it is                                                |
| --------------------------------------------------- | --------------------------------------------------------- |
| `Card` + `CardHeader` / `CardTitle` / `CardContent` | A muted card with a header band over an inset white panel |
| `Button`, `Badge`                                   | `cva` variants; `--app-control-height` tall, radius 8 px  |
| `Dialog`, `AlertDialog`, `Sheet`                    | Fade and zoom from 95%, a muted footer band               |
| `DropdownMenu`, `Popover`, `Select`, `Tooltip`      | Portalled, slide 2 units from their side                  |
| `Input`, `Textarea`, `Checkbox`, `Switch`, `Slider` | Form controls with a 3:1 border and a 3px focus ring      |
| `Sidebar`, `Breadcrumb`, `Separator`, `Skeleton`    | The shell and page furniture                              |

### Sizing and spacing

| Do                                                                | Don't                                |
| ----------------------------------------------------------------- | ------------------------------------ |
| `fontSize: '0.8125rem'`                                           | `fontSize: 13` (React makes this px) |
| `className='w-52'` or `w-[13rem]`                                 | `style={{ width: 208 }}`             |
| `calc(0.75rem * var(--app-density, 1))` for density-aware spacing | A fixed gap that ignores density     |
| `var(--app-muted)`                                                | A hex value in a component           |

`1px` hairlines, borders, shadows, outlines, transforms, and media queries may stay in px. Add a build script that fails on other px lengths, because this rule is easy to break unnoticed.

### Responsive layout

`.app-page` is the query container, so pages respond to the content area:

```css
@container (max-width: 43rem) {
	.record {
		grid-template-columns: 1fr;
	}
}
```

```tsx
<div className='@container/main'>
	<div className='grid grid-cols-1 gap-4 @xl/main:grid-cols-2 @5xl/main:grid-cols-3'>{/* cards */}</div>
</div>
```

| Size | Window | Container equivalent |
| ---- | ------ | -------------------- |
| `xs` | `36em` | `17rem`              |
| `sm` | `48em` | `29rem`              |
| `md` | `62em` | `43rem`              |
| `lg` | `75em` | `56rem`              |
| `xl` | `88em` | `69rem`              |

Use window media queries only for the shell. In Tailwind, use the `sm:`/`md:`/`lg:` variants (48rem is `md`); in CSS Modules, write the media query in rem (`@media (max-width: 47.99em)`).

Tables scroll inside their own wrapper, never the whole page.

### Motion

| Use                | Duration        | Easing                        |
| ------------------ | --------------- | ----------------------------- |
| Hover and press    | 90 ms           | `cubic-bezier(.2,.8,.2,1)`    |
| Small state change | 160 ms          | Same                          |
| Modal              | 180 ms          | Same                          |
| Sidebar width      | 200 ms          | Same                          |
| Drawer             | 220 ms          | Same                          |
| Page out / in      | 160 ms / 260 ms | `(.4,0,1,1)` / `(.2,.8,.2,1)` |

Motion confirms actions and is never required to understand them. Always honour reduced motion:

```css
@media (prefers-reduced-motion: reduce) {
	*,
	*::before,
	*::after {
		transition-duration: 0s !important;
		animation-duration: 0s !important;
	}
}
```

### Optional appearance settings

Write settings to `<html>` and style them in `tokens.css`. Store them on the server, and keep a copy in localStorage so the first paint is correct.

| Setting        | Mechanism                                                                 |
| -------------- | ------------------------------------------------------------------------- |
| Theme          | The `dark` class on `<html>` (light, dark or follow the system)           |
| Text size      | Root `font-size`; the whole UI scales                                     |
| Density        | `data-density="compact"` sets `--app-density: 0.7` and scales `--spacing` |
| High contrast  | `data-contrast="high"` overrides line and muted tokens                    |
| Reduced motion | `data-motion="reduce"` sets all durations to zero                         |

### Optional runtime branding

For a white-label system, serve an accent colour and logo in the app config. Set `--app-brand-accent` on `<html>`, and have tokens read `var(--app-brand-accent, #2563eb)`. The router loads the config below the theme provider, so publish branding to a small store and have a wrapper around the provider subscribe with `useSyncExternalStore`.

### Detail page

Use a multi-column layout driven by container queries. Show cached data immediately, and refresh it in the background. Show a spinner only when there is nothing to display.

### Required states

| State                    | Pattern                          |
| ------------------------ | -------------------------------- |
| Loading with no data     | Spinner or skeleton              |
| Refreshing existing data | Keep the content visible         |
| Load failure             | Inline error with a retry button |
| Empty                    | Message with the next action     |
| Action failed            | Red notification with the reason |
| Reversible action        | Toast with Undo                  |
| Destructive action       | Confirmation modal               |
| No permission            | `PermissionGate` message         |

### Data rules

- Use relative API paths, and proxy them in development. Same-origin requests keep session cookies first-party.
- Treat a 401 in one shared place: clear the session, then redirect to `/login` with the return path.
- Keep one cache for each kind of server data.

```ts
// vite.config.ts
plugins: [
  tanstackRouter({ target: 'react', autoCodeSplitting: true }), // Before react()
  react(),
],
server: {
  proxy: { '/api': { target: 'http://localhost:3001', changeOrigin: false } },
},
```

Static hosting needs an SPA fallback, or refreshing a client-side route returns a 404:

```nginx
location /assets/ { expires 1y; add_header Cache-Control "public, immutable"; try_files $uri =404; }
location = /index.html { add_header Cache-Control "no-store"; }
location / { try_files $uri $uri/ /index.html; }
```

## 10. Recipes

### Add a page

1. Build the page in `src/feature/<domain>/index.tsx`.
2. Add `src/routes/_protected/<domain>.tsx`.
3. If it has children, make that file a layout with `<Outlet />`, and add `<domain>.index.tsx` and `<domain>.$id.tsx`.
4. Add a `beforeLoad` redirect if a feature flag controls it.
5. Run the dev server once to regenerate the route tree.
6. Add a `NavLink`. The sidebar, breadcrumb, search, and shortcut follow from it.

### Add a tab

1. Add `<domain>.<tab>.tsx` as a child route.
2. Add it to the parent layout's `TABS`.
3. Add the segment to the `NavLink`'s `tabs`.

### Add a public link page

Create it at the top level of `routes/`, outside `_public` and `_protected`, with the token in the path.

## 11. Applying this to a new system

1. Scaffold Vite, Tailwind v4, the shadcn components you need, the router plugin, and the dev proxy.
2. List your system's domains, then map them to routes and menu sections.
3. Replace the token values and fonts, then confirm light and dark mode work on stock components.
4. Implement `fetchAppConfig()` and `fetchSession()` against your backend.
5. Add `__root`, `_public/login`, `_protected`, and sign-in and sign-out.
6. Add `AppLayout`, `Sidebar`, `TopBar`, and `navigation.ts`.
7. Build one complete feature (list, detail, form) as the template for the others.
8. Add shortcuts, search, and the optional settings last.

Drop anything your system doesn't need. The optional parts are the scope switcher, pinned pages, feature flags, appearance settings, and runtime branding. The rest of the pattern works without them.
